# Unconditional Flow Matching With Classifier-Based Pruning for Distribution-Aligned Soil Spectral Synthesis

Code and results for the IEEE *Geoscience and Remote Sensing Letters* paper
[10.1109/LGRS.2026.3721837](https://doi.org/10.1109/LGRS.2026.3721837).

We generate synthetic soil data from the LUCAS 2015 topsoil database with unconditional
Flow Matching, then remove out-of-distribution artifacts with a stochastic
classifier-based pruning filter. On the most complex subset (4,257 samples, 12 tabular
features and 4,200-dimensional spectra) pruning lowers the adversarial AUC from 0.6996 to
0.6133, moving the synthetic joint distribution measurably closer to the real one.

Every table and figure in the letter regenerates from the files committed here.

## What is in this repository

```
flowMatching/          Flow Matching model, transforms, training loop
eval/                  Experiment drivers and the evaluation pipeline
notebooks/             Colab runners (01, 02) and the results notebook (03)
scripts/               patch_tabsyn.sh — required TabSyn compatibility patch
paths.py               Canonical output locations, used by every script
prepare_datasets.py    Builds the four dataset variants from raw LUCAS

results/
├── flow_matching/     Our per-iteration AUCs (100 Monte Carlo runs)
├── tabsyn/            TabSyn baseline AUCs (20 runs)
├── downstream/        PLSR train-on-synthetic utility metrics
├── tables/            Generated LaTeX — identical to the published tables
└── figures/           Generated figures — identical to the published figures
```

The committed results are small (about 2.6 MB in total): 100 Monte Carlo runs contribute one
row of AUC values each, so the full evidence base for Table I is well under a megabyte. The
per-iteration sample dumps those runs also produce are roughly 5.9 GB, are regenerable, and
are deliberately **not** committed — no published number depends on them.

The one exception is
`results/flow_matching/chem_phys_spectral/saved_samples_iter_0/`, where four artifacts
(595 KB) *are* committed so Figure 1 can be redrawn without re-running the whole loop.

### What those four artifacts contain

They hold no LUCAS records. The raw archives and `data/prepared_datasets/` are excluded by
`.gitignore`; what is committed here is derived from the 2,979-sample training split of
iteration 0, or generated by the model:

| File | Contents |
|---|---|
| `fm_scaler_iter.pkl` | Feature means and standard deviations (12 tabular, 4,200 spectral bands) and an 8-component spectral PCA basis — the mean spectrum plus 8 loading vectors |
| `fm_transform_params.pkl` | Quantile thresholds for the log-linear, piecewise-exponential and dequantisation transforms |
| `pure_test.parquet` | 639 model-generated records, unpruned |
| `pruned_test_0.5.parquet` | 639 model-generated records, after pruning at *r* = 0.50 |

`fm_scaler_iter.pkl` and `fm_transform_params.pkl` are Python pickles; only load them from a
checkout you trust.

Every value is either an aggregate over 2,979 samples or synthetic model output. No
`Point_ID`, coordinates or geometry appear in any of them, and no individual sample is
recoverable from a rank-8 subspace and a mean. `Elevation` occurs only as an aggregate
mean/standard deviation and as synthetic values. This is the same class of aggregate the
letter already publishes as Figure 1(b), the real mean spectrum ± 1 SD.

To rebuild them instead, run one iteration into a scratch directory and copy
`saved_samples_iter_0/` across:

```bash
PYTHONPATH=. python eval/validation_pipeline.py \
    --mode chem_phys_spectral --N 1 --output_dir /tmp/fm_iter0
```

Use a scratch `--output_dir`. Pointing it at the committed folder would overwrite the
100-iteration `phase*.csv` with single-iteration data.

## Setup

```bash
python -m venv venv
./venv/bin/pip install -r requirements.txt
```

`torchdiffeq` is a hard dependency — the learned vector field is integrated with it — and is
easy to miss when installing by hand.

PyPI's Linux `torch` wheel is CUDA-only — on ROCm or CPU, install the build for your hardware
from [pytorch.org](https://pytorch.org/get-started/locally/) first.

### Data

LUCAS 2015 is distributed by the [European Soil Data Centre
(ESDAC)](https://esdac.jrc.ec.europa.eu/projects/lucas) under its own access conditions and
is **not** redistributed here. Access requires registration, and the licence grants a
personal, non-transferable right to use the data with no sub-licensing; aggregated results
may be published. Request the topsoil database and the soil spectral library, then place
them as:


## Reproducing the comparison: ours vs. TabSyn

Both pipelines derive iteration *i* from `seed = 42 + i` and split 70/15/15 with that seed.
Run *i* of our model and run *i* of TabSyn therefore see **identical train/validation/test
partitions**, which is what makes the two AUC columns directly comparable.

### 1. Our method — 100 iterations

```bash
PYTHONPATH=. python eval/run_flow_pruning.py --N 100
```

Writes, for each variant, to `results/flow_matching/<variant>/`:

| File | Contents |
|---|---|
| `phase1_val_results.csv` | validation AUC per iteration and threshold — used to pick *r* |
| `phase1_rejection_rates.csv` | validation rejection rates — Figure 2 |
| `phase2_test_results.csv` | **test AUC at 1x — Table I** |
| `phase2_test_results_10x.csv` | test AUC at 10x — Table II |
| `phase2_test_rejection_rates.csv` | test rejection rates — Table I |
| `phase2_test_generation_times.csv` | sampling times |
| `train_times.csv` | per-iteration seeds and training times — the 12.60 s figure |
| `saved_samples_iter_*/` | generated samples and scalers (large, not committed) |

Each run also drops a `metadata.json` inside every `saved_samples_iter_*/`;
`train_times.csv` consolidates them so the committed results are eight readable CSVs per
variant rather than a hundred single-file directories.

### 2. TabSyn baseline — 20 iterations

```bash
git clone https://github.com/amazon-science/tabsyn.git
./venv/bin/pip install -r requirements-tabsyn.txt
./venv/bin/pip install --no-deps zero ply quantiphy   # zero pins Click==7.0
bash scripts/patch_tabsyn.sh          # required — see below

PYTHONPATH=. python eval/run_tabsyn_baseline.py --start 0  --end 2
PYTHONPATH=. python eval/run_tabsyn_baseline.py --start 2  --end 4
PYTHONPATH=. python eval/run_tabsyn_baseline.py --start 4  --end 10
PYTHONPATH=. python eval/run_tabsyn_baseline.py --start 10 --end 20
```

`--end` is exclusive. These four chunks produce exactly the committed filenames
(`tabsyn_baseline_0_to_1.csv`, `2_to_3`, `4_to_9`, `10_to_19`) in
`results/tabsyn/<variant>/`.

**Why it is chunked, and why 20 rather than 100.** TabSyn costs 888.52 s per iteration to
train on the Comprehensive Joint Set, against 12.60 s for our model — roughly 70x. Summed
across the four variants one iteration is about 4,794 s, so 20 iterations amount to
**around 27 hours of training**, which outlasts a single Colab session. Our own pipeline
measures 55.1 / 56.7 / 11.7 / 12.6 s per iteration for the four variants, with sample
generation and the XGBoost AUC over 11 thresholds on top.

`scripts/patch_tabsyn.sh` is **not optional**: TabSyn passes `verbose=True` to a scheduler
signature that no longer accepts it, and its VAE training raises `TypeError` without the
patch. The script is idempotent.

### 3. Downstream utility

```bash
for v in chem_nospectral chem_spectral chem_phys_nospectral chem_phys_spectral; do
    PYTHONPATH=. python eval/evaluate_downstream.py --mode "$v" --N 10
done
```

Trains PLSR to predict organic carbon under train-on-real and train-on-synthetic protocols,
with a paired Wilcoxon test against the real baseline. Writes
`results/downstream/<variant>/downstream_metrics_PLSR.csv`. This step reads TabSyn's
generated files from `tabsyn/data/<variant>/`, so run step 2 first if you want the TabSyn
rows.

### 4. Tables and figures

Run [`notebooks/03_generate_paper_results.ipynb`](notebooks/03_generate_paper_results.ipynb).
It rebuilds `results/tables/` and `results/figures/` byte-for-byte identically to the
published artifacts.

To run it headlessly instead of interactively:

```bash
./venv/bin/jupyter nbconvert --to notebook --execute --inplace notebooks/03_generate_paper_results.ipynb
```

## Implementation details behind the letter

GRSL letters run to five pages, so the paper states the method compactly. These are the
details it leaves implicit, for anyone reading the code alongside it.

### Which split each stage uses

The validation protocol splits 70/15/15 per iteration. Within one iteration
([`eval/validation_pipeline.py`](eval/validation_pipeline.py)):

| Step | Split used |
|---|---|
| Flow Matching training, with early stopping | train / validation |
| Synthetic pool for fitting the pruning tree | generated at training-set size |
| Pruning decision tree fitted (real vs. synthetic) | training |
| Candidate thresholds scored by adversarial AUC | validation |
| Threshold selected (minimum mean + 1 SD across runs) | validation, across all *N* runs |
| Final reported AUC | held-out test |

The rejection threshold *r* is the tuned hyperparameter, and it is selected on the validation
split exactly as the letter describes. The tree's structure is fitted on the training split,
so no validation data enters the tree, and no test data enters either stage.

### What each timer covers

Both runtimes are measured end-to-end over their phase, on the same basis for either method:

| Field | Covers |
|---|---|
| ours, `time_train_sec` | Flow Matching training, the pruning-tree fit, validation-batch generation, and one XGBoost AUC |
| TabSyn, `Time_Train_Sec` | `process_dataset.py` preprocessing, VAE training, and diffusion training |

Measuring both inclusively keeps the comparison like-for-like, and is conservative for our
method: the post-training steps above are charged to the 12.60 s.

The per-sample rates in the letter divide the recorded sampling times by the rows each call
produces. Both denominators are worth stating, since neither is the test-set size by default:

| | sampling time | rows | rate |
|---|---|---|---|
| ours (pruned) | 0.1021 s | 639 delivered | **0.16 ms/sample** |
| TabSyn (1x) | 5.6835 s | 2,979 generated | **1.91 ms/sample** |

TabSyn emits one training-split worth of rows per sampling call rather than honouring a
requested count, hence 2,979. Ours counts the 639 samples actually delivered, so the cost of
candidates discarded by pruning is charged to our own rate. Both recompute from
`results/flow_matching/*/phase2_test_generation_times.csv` and
`results/tabsyn/*/tabsyn_baseline_*.csv`.
